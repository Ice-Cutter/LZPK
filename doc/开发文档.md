# 一、游戏设计

## 1.1 基本信息

| 项目 | 内容 |
|------|------|
| 游戏名称 | PK Runner（暂定） |
| 游戏类型 | 2D 横板无限跑酷 |
| 参考游戏 | Chrome Dino (T-Rex Runner) |
| 目标平台 | Web / 移动端 |
| 开发引擎 | Cocos Creator 3.8.8 |
| 开发语言 | TypeScript |
| 包体大小 | < 5MB（不含引擎） |
| 帧率目标 | 稳定 60 FPS |
| 首屏加载 | < 3 秒 |

**游戏简介**：一款像素风格的 2D 横板无限跑酷游戏。玩家操控角色自动向右奔跑，通过跳跃和下蹲躲避障碍物。速度逐渐加快，难度递增，挑战反应极限。

---

## 1.2 核心玩法

### 操作方式

| 操作 | 键盘 | 触屏（手机） |
|------|------|------|
| 跳跃 | Space / ↑ / W | 按右下绿色「跳」按钮 |
| 下蹲 | ↓ / S | 按住左下蓝色「蹲」按钮 |
| 站起 | 松开 ↓ / S | 松开「蹲」按钮 |
| 重新开始 | Space / Enter | 点击屏幕任意位置 |

### 角色能力

- **跳跃**：原地跳起跨越地面障碍物。按住跳跃键延长滞空（高跳），快速点击为短跳。
- **下蹲**：缩小身形躲避空中障碍物，碰撞体同步缩小。空中不可下蹲。
- **二段跳**（V1.2 可选）：空中可再跳一次。

### 得分规则

- 每前进一段距离 +1 分（随游戏速度变化）
- 右上角实时显示当前分数
- 游戏结束显示当前分数与历史最高分
- 每 100 分触发一次里程碑提示

## 1.3 障碍物类型

| 类型 | 描述 | 躲避方式 | 出现条件 |
|------|------|----------|----------|
| 小型仙人掌 | 矮障碍物，1 单位宽 | 跳跃 | 始终 |
| 大型仙人掌 | 高障碍物，2 单位宽 | 跳跃 | 分数 > 100 |
| 仙人掌群 | 3 个小型仙人掌排列 | 跳跃 | 分数 > 300 |
| 飞鸟（低飞） | 空中障碍物，低空 | 跳跃或下蹲 | 分数 > 200 |
| 飞鸟（高飞） | 空中障碍物，高空 | 下蹲 | 分数 > 450 |
| 飞鸟群 | 2-3 只交替高低飞 | 下蹲 | 分数 > 700 |

## 1.4 游戏流程

### 三态状态机

```
┌──────────┐    点击开始    ┌──────────┐
│  START   │──────────────→│ PLAYING  │
│  开始界面 │               │  游戏中   │
└──────────┘               └────┬─────┘
                                │ 碰撞障碍物
                                ↓
                          ┌──────────┐
                          │ GAME_OVER│
                          │  结束界面 │
                          └────┬─────┘
                               │ 点击重新开始 → PLAYING（循环）
```

### 各状态说明

**START（开始界面）**
- 显示游戏标题/Logo 和操作提示，背景静止，角色站立待机

**PLAYING（游戏中）**
- 地面和背景滚动，障碍物随机生成，分数递增，速度增长

**GAME_OVER（结束界面）**
- 角色死亡动画，显示 "GAME OVER"、当前分数和最高分，破纪录显示 "NEW HIGH SCORE!"

| 分数区间 | 生成间隔 | 说明 |

| 0 - 200 | 2.0 - 3.0s | 间歇稀疏 |
| 200 - 500 | 1.5 - 2.5s | 密度增加 |
| 500 - 1000 | 1.0 - 2.0s | 中等密度 |
| 1000 - 2000 | 0.8 - 1.5s | 较高密度 |
| 2000+ | 0.5 - 1.2s | 高密度挑战 |

每 700 分切换一次昼夜，带过渡动画。

## 2.2 系统架构

```
┌────────────────────────────────────────────────────────────┐
│                      GameManager                           │
│                 (游戏状态机 · 全局调度)                      │
└──────┬──────────┬──────────┬──────────┬───────────────────┘
       ↓          ↓          ↓          ↓
┌──────────┐┌──────────┐┌──────────┐┌──────────┐
│  Player  ││ Obstacle ││   Env    ││    UI    │
│Controller││ Spawner  ││ Scroller ││  Manager │
└──────────┘└──────────┘└──────────┘└──────────┘
       │          │          │          │
       └──────────┴──────────┴──────────┘
                       │
                       ↓
              ┌─────────────────┐
              │    EventBus     │  (全局事件通信)
              └─────────────────┘
```

**通信优先级**：EventBus 全局事件（跨模块）> @property 节点引用（父子/同层）> getComponent（同节点组件间）。禁止使用 `find()` 查找节点。

- **职责**：状态机管理、速度控制、分数计算、难度递增


- **状态**：`IDLE` / `RUNNING` / `JUMPING` / `CROUCHING` / `DEAD`

```typescript
playerState: PlayerState;    // 玩家状态
jumpForce: number;           // 跳跃力度 (默认 600)
gravity: number;             // 重力 (默认 -2000)
isGrounded: boolean;         // 是否着地
```

### ObstacleSpawner
- **职责**：障碍物随机生成、对象池管理、频率控制

```typescript
obstaclePools: Map<string, ObjectPool>;
spawnTimer: number;
spawnIntervalRange: Vec2;
availableTypes: ObstacleType[];
// 方法：spawnObstacle() / recycleObstacle() / updateDifficulty(level)
```

### GroundScroller
- **职责**：双地面块交替循环，超出左侧后移至右侧

### UIManager
- **职责**：UI 面板显示/隐藏切换，持有 ScoreDisplay 和 CoinCounter 引用，在面板切换时同步更新


- **职责**：独立的分数 UI 显示组件，监听 SCORE_CHANGE 事件更新当前分数

## 2.6 碰撞检测

### 物理配置

- 使用 Box2D 2D 物理引擎
- 碰撞分组：Group 1 (Player) / Group 2 (Ground) / Group 3 (Obstacle)
- 检测规则：Player ↔ Obstacle（游戏结束）| Player ↔ Ground（着地）

### 碰撞回调

```typescript
// PlayerController.ts
onBeginContact(self: Collider2D, other: Collider2D, contact: IPhysics2DContact) {
    if (other.group === CollisionGroup.OBSTACLE) {
        this.die();
        EventBus.emit(GameEvent.PLAYER_DIE);
        EventBus.emit(GameEvent.GAME_OVER);
    }
    if (other.group === CollisionGroup.GROUND) {
        this.onLand();
    }
}
```

## 2.8 关键技术实现

### 地面无限滚动（三瓦片双缓冲循环）

#### 核心原理

使用多块相同尺寸的地面瓦片首尾相接排列，每帧匀速左移。当最左侧瓦片完全移出屏幕后，将其重新放置到最右侧瓦片末尾，形成无限循环。

**初始设计为 2 瓦片，Bug 修复后升级为 3 瓦片系统。**

#### 坐标系关键参数

| 参数 | 值 | 说明 |
|------|-----|------|
| 瓦片宽度 | 1920 px | `UITransform.contentSize.width`，锚点 (0.5, 0.5) |
| 设计分辨率 | 1920 × 1080 | SHOW_ALL 策略 |
| 摄像机可视 X 范围 | [-960, 960] | 半宽 = 1920 / 2 |
| 瓦片初始排列 | [-960, 960, 2880] | 3 瓦片首尾相接 |

#### 回收阈值数学推导

瓦片右边缘 = `position.x + tileWidth / 2`

摄像机左边缘 = `-tileWidth / 2 = -960`

回收条件：瓦片右边缘完全离开摄像机左边缘后，再有半瓦片宽度的安全缓冲：

```
position.x + tileWidth/2 ≤ -tileWidth/2 - tileWidth/2
position.x ≤ -tileWidth × 1.5
position.x ≤ -1920 × 1.5 = -2880
```

**为什么 2 瓦片系统无法安全延后回收：**

| 时刻 | Tile0 位置 | Tile1 位置 | 屏幕覆盖 | 状态 |
|------|-----------|-----------|---------|------|
| 0s | -960 | 960 | 全覆盖 | ✓ |
| 2.4s (960px) | -1920 | 0 | 全覆盖 | ✓（旧阈值触发回收） |
| 2.41s | -1924 | -4 | 右半空缺 | ✗ 缝隙开始出现 |
| 4.8s | -2880 | -960 | 左半/Tile1，右半/Tile2 | ✓（新阈值触发回收） |

**结论**：2 瓦片下，只要回收阈值比 `-1920` 更负，Tile1 必然在 Tile0 被回收前移过 x=0，屏幕右半边 `[0, 960]` 出现空白。**必须至少 3 瓦片才能同时满足"延后回收"和"无缝隙"。**

#### 三瓦片系统运行时状态

```
初始:  [T0@-960,  T1@960,  T2@2880]    屏幕[-960,960]←T0右半+T1左半 ✓
4.8s:  [T0@-2880, T1@-960, T2@960]     T0回收→移到T2右侧→[T1,T2,T0@2880] ✓
9.6s:  [T1@-2880, T2@-960, T0@960]     T1回收→[T2,T0,T1@2880] ✓
                                                      ↑ 循环往复
```

#### GroundScroller 完整实现

**文件**：`assets/scripts/environment/GroundScroller.ts`

```typescript
@ccclass('GroundScroller')
export class GroundScroller extends Component {
    @property([Node]) groundTiles: Node[] = [];

    private _speed: number = 0;
    private _tileWidth: number = 0;
    private _recycleThreshold: number = 0;

    onLoad(): void {
        // 读取瓦片宽度，计算回收阈值
        const ui = this.groundTiles[0].getComponent(UITransform);
        this._tileWidth = ui ? ui.width : 0;
        this._recycleThreshold = -this._tileWidth * 1.5;  // -2880
        // 注册事件...
    }

    start(): void {
        this._ensureTileCount(3);   // 不足 3 块时自动克隆补齐
        this._resetTilePositions(); // 并排放置
    }

    update(deltaTime: number): void {
        if (this._speed <= 0 || state !== PLAYING || tiles.length < 3) return;
        // 全部左移
        for (const tile of this.groundTiles) {
            tile.setPosition(tile.position.x - this._speed * deltaTime, ...);
        }
        // 双缓冲回收
        const first = this.groundTiles[0];
        if (first.position.x <= this._recycleThreshold) {
            let rightmostX = -Infinity;
            for (const tile of this.groundTiles) {
                if (tile.position.x > rightmostX) rightmostX = tile.position.x;
            }
            first.setPosition(rightmostX + this._tileWidth, ...);
            this.groundTiles.push(this.groundTiles.shift()!);
        }
    }

    private _ensureTileCount(minCount: number): void {
        // 不足时 clone 第一块瓦片补齐
        while (this.groundTiles.length < minCount) {
            const clone = instantiate(this.groundTiles[0]);
            clone.parent = this.groundTiles[0].parent;
            this.groundTiles.push(clone);
        }
    }

    private _resetTilePositions(): void {
        const startX = -this._tileWidth / 2;
        for (let i = 0; i < this.groundTiles.length; i++) {
            this.groundTiles[i].setPosition(startX + i * this._tileWidth, ...);
        }
    }

    private _onGameRestart(): void {
        this._resetTilePositions();
        this._speed = 0;
    }
}
```

**关键设计决策**：

- **`start()` 而非 `onLoad()` 中定位瓦片**：编辑器场景中两瓦片默认位置均为 (0,0)，重叠在一起。必须在组件启动时显式排列。`onGameRestart` 不触发 `start()`，所以 `_onGameRestart` 也需调用 `_resetTilePositions`。
- **`_ensureTileCount()` 自动补齐**：不依赖编辑器配置，运行时动态克隆确保至少 3 瓦片。不足 3 块时 `update()` 提前返回（安全防护）。
- **使用 `instantiate()` 而非 `Node.instantiate()`**：`instantiate` 是 `cc` 模块导出的独立函数，不是 `Node` 的静态方法。后者是运行时错误。

### 视差滚动背景
```
远层速度 = baseSpeed × 0.2
中层速度 = baseSpeed × 0.5
近层速度 = baseSpeed × 0.8
```
每层同样使用双块循环。

## 3.2 组件开发规范

### 三项原则

1. **单一职责**：每个组件只负责一项功能（✅ PlayerController + PlayerAnim 分开，❌ 大杂烩）
2. **依赖注入**：通过 `@property` 编辑器拖拽绑定，不写死引用
3. **事件解耦**：跨模块通信用 EventBus.emit()，不直接调用

### 生命周期指南

| 方法 | 适合 | 避免 |
|------|------|------|
| `onLoad()` | 初始化自身、注册事件 | 访问其他组件未初始化数据 |
| `start()` | 依赖其他组件的首次逻辑 | 异步数据 |
| `update(dt)` | 逐帧移动/计时 | 大量计算、频繁资源操作 |
| `onDestroy()` | 移除事件、清理定时器、释放资源 | 访问已销毁节点 |

### 禁止事项

- ❌ `update()` 中频繁 `getComponent()`（应 onLoad 缓存）
- ❌ `cc.find()` 查找（用 `@property` 绑定）
- ❌ `onLoad()` 中访问其他节点组件
- ❌ `setTimeout` / `setInterval`（用 `scheduleOnce` / `schedule`）
- ❌ 事件回调忘记移除监听
- ❌ 直接修改其他组件私有属性

### EventBus——target 绑定

```typescript
interface Listener {

    target?: any;
```

### 障碍物创建——放弃 Prefab 和 instantiate

**问题**：`instantiate()` 对编辑器场景节点上自定义组件的克隆不稳定，UUID 编码格式导致组件丢失。

**最终方案**：`ObstacleSpawner` 用 `PRESETS` 数组定义 5 种障碍物的基础尺寸和颜色，通过 `createObstacleNode()` 函数程序化创建节点（UITransform + Sprite/Graphics + BoxCollider2D + RigidBody2D + Obstacle），适配 ObjectPool 工厂模式。支持 SpriteFrame 图片和 Graphics 纯色两种渲染模式。

**注意**：函数参数名不能与局部变量重名（`g` 同时用作颜色绿值和 Graphics 变量）。

```typescript

// 碰撞体自动 = 视觉 × COLLIDER_W_RATIO(0.8) × COLLIDER_H_RATIO(0.9)
const PRESETS: [string, number, number, number, number, number, number][] = [
    [ObstacleType.CACTUS_SMALL,  40,  80, 121,  85,  72,   0],

    // 低飞鸟 60×30, center=80,  yOff=65: 碰站立, 下蹲安全, 跳跃越过
    [ObstacleType.BIRD_LOW,      60,  30, 244,  67,  54,  65],
    // 高飞鸟 60×70, center=140, yOff=105: 飞过站立头顶, 封跳跃, 下蹲安全
    [ObstacleType.BIRD_HIGH,     60,  70, 233,  30,  99, 105],
```

### 视觉渲染——Sprite（图片） vs Graphics（纯色）双模式

障碍物创建时根据是否提供了 SpriteFrame 选择渲染方式：

- **图片模式**（提供了 SpriteFrame）：创建 `Sprite` 组件，`sizeMode=CUSTOM` 填充 UITransform 区域。缩放时只需调整 UITransform，Sprite 自动适配。
- **纯色模式**（SpriteFrame 为空）：创建 `Graphics` 组件，`fillColor + rect + fill` 绘制矩形。缩放时需 `clear() + 重绘`。

两种模式在 `_applyScaleToNode()` 中分支处理，`(node as any)._hasSprite` 标记区分。

### PlayerAnim——外观定制

支持两种外观模式，所有属性在编辑器中可调：

**颜色属性（`@property`）**：纯色模式或图片染色

- `colorJump`：跳跃（默认浅绿 #8BC34A）
- `colorCrouch`：下蹲（默认深绿 #388E3C）

## 5.5 碰撞检测

### 方案：手动 AABB 重叠检测

**放弃 Box2D 物理碰撞回调**，改为每帧在 `Obstacle.update()` 中手动计算 AABB（轴对齐包围盒）交叠。

**原因**：Box2D 中两个 Kinematic 刚体不产生碰撞事件，尝试过多种组合均失败：

| 尝试 | Player | Obstacle | 结果 |
|------|--------|----------|------|
| 原始方案 | Kinematic | Kinematic | ❌ Kinematic ↔ Kinematic 不碰撞 |
| Static 方案 | Kinematic | Static | ❌ `node.setPosition()` 不同步 Static 物理体 |
| Dynamic 方案 | Kinematic | Dynamic | ❌ `linearVelocity` 用物理单位(m)，PTM=32 导致速度 ×32 |

**Obstacle.ts** — 每帧移动后手动计算 AABB：

```typescript
    const player = PlayerController.instance;
    if (player && this._collider) {
        if (this._checkCollision(player)) {
            player.die();
            return;
        }
    }
}

private _checkCollision(player: PlayerController): boolean {
    // 用 node.position + collider.size + collider.offset 计算矩形
    // 返回两个矩形的交叠判断: oL < pR && oR > pL && oB < pT && oT > pB
}
```

**PlayerController.ts** — 新增静态单例供 Obstacle 引用：

```typescript
private static _instance: PlayerController = null;
static get instance(): PlayerController { return PlayerController._instance; }
```

## 5.6 踩坑记录

### 1. 手写场景 JSON 导致编辑器崩溃

**现象**：手写生成的 Game.scene 导致 `postSettings.activate is not a function`、`Render frame was disposed` 等一系列崩溃。

**原因**：手写 JSON 无法创建 Cocos 类实例（缺少 `activate()` 等生命周期方法），Plain Object 与 Class Instance 不兼容。

**解决**：完全在编辑器中手动创建场景节点。

### 2. `@property` 不能用于 `private` 字段

**现象**：`@property private _debugMode` 导致 GameManager 编译失败，进而导致整个导入链（SceneBuilder、其他组件）全部不可用。

**解决**：`@property` 只用于 `public` 字段，私有字段不加装饰器。

### 3. 模块 `cc` 无法解析

**现象**：`Unable to resolve bare specifier 'cc'`。

**原因**：`temp/programming/` 缓存被清理后，SystemJS 的 `cc → cce:/internal/x/cc` 映射未建立。

**解决**：完全重启编辑器（冷启动），自动重建编译缓存。

### 4. UUID 编码格式不一致

**现象**：场景 JSON 中 `__type__` 使用压缩 UUID（如 `87f21IyZ...`），而 `.meta` 使用标准 hex UUID（如 `87f21232-...`）。手写组件引用时用 hex UUID 导致组件"missing or invalid"。

**解决**：不要在场景 JSON 中手写自定义组件引用。所有组件通过编辑器 Add Component 添加。

### 5. `instantiate()` 对 scene node 的组件克隆不完整

**现象**：`instantiate(template)` 克隆的子节点缺少自定义组件（Obstacle）。

**解决**：改为程序化创建节点（`new Node()` + `addComponent()`），不依赖 `instantiate` 克隆 scene node。

### 6. 函数参数与局部变量重名

**现象**：`Identifier 'g' has already been declared.` — `createObstacleNode(..., g, ...)` 参数 `g`（颜色绿值）与 `const g = node.addComponent(Graphics)` 冲突。

**解决**：局部变量改名为 `gr`。

### 7. Box2D 物理碰撞回调无法触发

**现象**：Player 和 Obstacle 均配置了 RigidBody2D + BoxCollider2D + enabledContactListener，但 `BEGIN_CONTACT` 回调从未触发，碰撞无反应。

**原因**：Box2D 中两个 **Kinematic** 刚体不产生碰撞事件（`Kinematic ↔ Kinematic → No Contact`）。尝试将 Obstacle 改为 Static 后，`node.setPosition()` 移动不会同步到 Box2D 的 Static 物理体位置；改为 Dynamic 并用 `linearVelocity` 驱动后，速度单位从像素/秒变成物理单位米/秒（PTM=32），障碍物速度暴增 32 倍。

**解决**：完全放弃 Box2D 物理碰撞回调，改为在 `Obstacle.update()` 中手动计算 AABB（轴对齐包围盒）矩形交叠。用 `node.position + collider.size + collider.offset` 得出两个碰撞盒的世界坐标矩形，判断四边是否重叠。简单、可靠、不受 Box2D 规则约束。

## 5.7 外观缩放系统——视觉与碰撞等比联动

> **设计目标**：修改玩家/障碍物的外观大小时，碰撞体积等比跟随，保持游戏手感一致。支持导入 PNG 图片替换纯色占位。

### 核心架构

```
视觉参数（PRESETS / @property）
    ↓ 基准尺寸(baseW, baseH)
UITransform.setContentSize(baseW × scale, baseH × scale)   ← 视觉
    ↓ × COLLIDER_RATIO(0.8, 0.9)
BoxCollider2D.size = visual × 0.8, visual × 0.9           ← 碰撞
    ↓
AABB 碰撞检测（Obstacle._checkCollision）                    ← 手感
```

**缩放链路**：改 `scale` → UITransform 变大 → BoxCollider2D 等比变大 → AABB 范围变大 → 碰撞判定自然适配。

### Player 缩放

`PlayerController.playerScale`（`@property`，默认 1.0）

- `onLoad()` 记录编辑器设定值为基准（`_baseVisualW/H`、`_baseColliderW/H`）
- `start()` 调用 `_applyScale()` → `UITransform × scale`、`BoxCollider2D.size × scale`
- 下蹲时碰撞体高度 = `_baseColliderH × playerScale × crouchScaleY(0.5)`
- 重新开始(`_onGameRestart`)时重新应用 scale 确保正确

```typescript
// PlayerController.ts
@property({ tooltip: '玩家整体缩放倍率（视觉+碰撞同步放大/缩小，1.0=默认）' })
playerScale: number = 1.0;

private _applyScale(): void {
    const s = this.playerScale;
    this._uiTransform.setContentSize(this._baseVisualW * s, this._baseVisualH * s);
    this._collider.size.width = this._baseColliderW * s;
    this._collider.size.height = this._baseColliderH * s;
}
```

### Obstacle 缩放

`ObstacleSpawner.obstacleScale`（`@property`，默认 1.0）

- PRESETS 存储 scale=1.0 时的基准尺寸（`_baseW/_baseH`）
- 每次 `_spawnObstacle()` 从对象池取出节点时，调用 `_applyScaleToNode()`
- 图片模式下只需调整 UITransform（Sprite.CUSTOM 自动填充）
- 纯色模式下还需 `Graphics.clear() + 重绘`
- 碰撞体始终 = `视觉 × COLLIDER_W_RATIO(0.8) × COLLIDER_H_RATIO(0.9)`
- Y 坐标直接从 UITransform 实际高度计算（不再依赖存储的 `_baseH`）：`y = GROUND_Y + yOff × scale + UITransform.height / 2`

```typescript
// ObstacleSpawner.ts
@property({ tooltip: '障碍物整体缩放倍率（视觉+碰撞同步）' })
obstacleScale: number = 1.0;

private _applyScaleToNode(node: Node): void {
    const s = this.obstacleScale;
    const vw = baseW * s, vh = baseH * s;
    ui.setContentSize(vw, vh);
    if (!hasSprite) { /* 重绘 Graphics */ }
    bc.size = new Size(vw * 0.8, vh * 0.9);
}

// 生成时 Y 坐标从 UITransform 直接读取（自适应）
private _spawnObstacle(): void {
    // ...
    const ui = node.getComponent(UITransform);
    const actualH = ui ? ui.height : 80;
    const y = yOff > 0
        ? GameConfig.GROUND_Y + yOff * this.obstacleScale + actualH / 2
        : GameConfig.GROUND_Y + actualH / 2;
    // ...
}
```

## 5.8 拾取物系统

> **设计目标**：跑酷途中自动生成金币和道具，玩家碰触即拾取，增加游戏变数和策略深度。

### 拾取物类型

| 类型 | 枚举值 | 视觉 | 分值 | 稀有度 | 额外效果 |
|------|--------|------|------|--------|---------|
| 金币 | `COIN` | 30×30 金色 | +10 | 70% | 无 |
| 护盾 | `SHIELD` | 34×34 蓝色 | +30 | 15% | 抵挡一次碰撞 |
| 磁铁 | `MAGNET` | 34×34 红色 | +20 | 10% | （预留） |
| 加速鞋 | `SPEED_BOOST` | 34×34 绿色 | +15 | 5% | 2秒×1.5倍速 |

### 架构

```
PickupSpawner (生成器)
  ├── ObjectPool ×4          # 每种类型独立对象池，预热 10 个
  ├── PRESETS 数组           # 基础尺寸和颜色
  ├── _buildCandidateYs()    # 5 个候选高度
  ├── _pickNonOverlappingY() # 选不重叠的高度
  ├── _cullOverlappingPickups() # 运行时持续清除重叠
  └── _visualOverlapsAny()   # AABB 视觉重叠判断

PickupItem (组件)
  ├── AABB 碰撞检测          # 同 Obstacle 的手动 AABB
  ├── 碰触即回收             # 无动画，直接 emit + recycle
  └── pickupType 枚举        # 标识拾取物类型
```

### 三层防重叠机制

拾取物和障碍物的生成计时器独立运行，存在"先放的拾取物被后放的障碍物覆盖"的竞态：

```
层级 1: PickupSpawner._spawnPickup()
  → _pickNonOverlappingY() 从 5 个候选高度中选不与障碍物重叠的

层级 2: ObstacleSpawner._spawnObstacle()
  → _overlapsAnyPickup() 检查是否与已有拾取物重叠，重叠则跳过

层级 3: PickupSpawner.update()
  → _cullOverlappingPickups() 每 0.15 秒全量扫描，移除任何重叠的拾取物
```

所有比对基于**视觉 AABB**（UITransform 宽高），不是碰撞体。

### 拾取物碰撞体

拾取物碰撞体使用 **1.5 倍**视觉尺寸（COLLIDER_W_RATIO = COLLIDER_H_RATIO = 1.5），使拾取判定范围比视觉更大，手感更宽松。例如 30×30 的金币实际碰撞体为 45×45。

### 事件流

```
PickupItem → AABB 碰触 → PICKUP_COLLECTED 事件
  → GameManager._onPickupCollected(type, points)
    → addScore(points)
    → 护盾: _shieldActive = true, emit SHIELD_ACTIVATED
    → 加速鞋: speedMultiplier=1.5, 倒计时 2s, emit POWERUP_START
```

### 护盾机制

护盾激活后，PlayerController.die() 内部检查 shieldActive → 如激活则设 1 秒无敌帧(invincible)，不进入 DEAD 状态：

```
碰撞 → die() → shieldActive? → invincible=true(1s) → emit PLAYER_DIE
  → GameManager._onPlayerDie → break shield → emit SHIELD_BROKEN
  → 同一障碍物后续帧碰撞 → die() → invincible=true → 提前返回
```

### 加速鞋机制

```
拾取 SPEED_BOOST → speedMultiplier=1.5, 倒计时 2s
  → _updateDifficulty() 发射 SPEED_CHANGE 时自动 × speedMultiplier
  → 倒计时结束 → speedMultiplier=1.0, 恢复原速
```

### 编辑器配置

在 GameWorld 下创建 `PickupContainer` 节点：
- UITransform(1920×1080)
- 挂载 `PickupSpawner` 组件
- 4 个 `@property SpriteFrame` 可选拖入贴图（留空=纯色）

## 5.9 自适应底部对齐

> **设计目标**：修改玩家、障碍物、拾取物的 UITransform 尺寸或 scale 属性后，底部自动对齐到 GROUND_Y，无需手动调整坐标。
>
> **2026-07-16 更新**：GROUND_Y 从 -400 改为 **0**（视角垂直中央），详见 5.11 节第 12 条。

### 核心规则

```
物体底部 = GROUND_Y(0)
物体中心 Y = GROUND_Y + UITransform.height / 2
```

所有 Y 坐标计算都直接从 `node.getComponent(UITransform).height` 读取，不依赖硬编码或存储值。

### Player 端

`PlayerController._syncGroundY()` — 新增方法，从当前 UITransform 高度计算 `groundY`：

```typescript
private _syncGroundY(): void {
    if (this._uiTransform) {
        this.groundY = GameConfig.GROUND_Y + this._uiTransform.height / 2;
    }
}
```

调用时机：
- `onLoad()` — 首次初始化
- `_applyScale()` — 每次缩放后自动调用
- 效果：改 `playerScale` 时 UITransform 变化 → groundY 自动跟随

**Player 初始位置保护**：`start()` 中强制 `setPosition(PLAYER_X, groundY, 0)`，防止编辑器拖拽残留。

**下蹲脚底保持**：`crouch()` 缩放前先下移 `(standingHalfH - crouchHalfH)` 补偿中心点偏移，脚底不悬空；`standUp()` 上移恢复。

### Obstacle 端

`ObstacleSpawner._spawnObstacle()` 的 Y 坐标从 UITransform 直接读取：

```typescript
const ui = node.getComponent(UITransform);
const actualH = ui ? ui.height : 80;
const y = GameConfig.GROUND_Y + actualH / 2;  // 底部 = GROUND_Y
```

不再依赖存储的 `(node as any)._baseH`。改 `obstacleScale` 或 PRESETS 高度时自动对齐。

### Pickup 端

`PickupSpawner._buildCandidateYs()` 基准高度从 PlayerController 的 UITransform 实时读取：

```typescript
const playerH = player.node.getComponent(UITransform)?.height || 90;
const playerRunY = GameConfig.GROUND_Y + playerH / 2;
```

拾取物尺寸也从 UITransform 读取而非存储值。

### 场景文件注意

`groundY` 作为 `@property` 会被序列化到 Game.scene。为让运行时自动计算生效，场景中 `groundY` 设为 0（代码检测到 0 时自动从 UITransform 计算）。Player 节点的 `_lpos` 也需与计算值一致（当前：x=-600, y=45）。

## 5.10 障碍物坐标设计——飞鸟高度

> 飞鸟作为空中障碍物，Y 位置必须精确计算，确保在各玩家状态下产生正确的碰撞行为。

### 坐标基准

> **2026-07-16 更新**：GROUND_Y 从 -400 改为 **0**（视角中央）。以下所有坐标已更新为当前值。

```
玩家站立:   节点中心=45,  碰撞体(60×90),  顶=90, 底=0
玩家下蹲:   节点中心=22.5, 碰撞体(60×45),  顶=45, 底=0
玩家跳跃峰值: 节点中心=190, 碰撞体(60×90), 顶=235, 底=145

障碍物 Y = GROUND_Y(0) + yOff + 视觉高度/2
碰撞体 = 视觉 × (0.8, 0.9)
碰撞条件(AABB): 障碍物底 < 玩家顶 && 障碍物顶 > 玩家底
```

### 低飞鸟：站立碰到 / 下蹲安全 / 跳跃越过

**约束推导**（GROUND_Y=0）：
- ① 站立碰撞：`colliderBottom < 90` → `center < 103.5`
- ② 下蹲安全：`colliderBottom > 45` → `center > 58.5`
- ③ 跳跃越过：`colliderTop < 145` → `center < 131.1`

→ `58.5 < center < 103.5`，选 **center=80, yOff=65**

```
60×30 yOff=65: 碰撞体 48×27, 底=66.5, 顶=93.5

站立: 底(66.5) < 顶(90) ✓ 碰撞  下蹲: 底(66.5) > 顶(45) ✗ 安全  跳跃: 顶(93.5) < 底(145) ✗ 越过
```

### 高飞鸟：站立安全（飞过头顶） / 下蹲安全 / 跳跃碰到

> **2026-07-16 重新设计**：高飞鸟原设计为 "站立碰到+跳跃封住"（yOff=85），与低飞鸟行为过于相似（站立都碰撞）。
> 新设计改为「飞过站立玩家头顶，只封跳跃路线」，与低飞鸟形成互补——低飞鸟迫使跳跃，高飞鸟迫使下蹲。

**约束推导**（60×70, 碰撞体48×63, 半高31.5, GROUND_Y=0）：
- ① 站立安全（飞过头顶）：`colliderBottom > 90` → `center - 31.5 > 90` → `center > 121.5`
- ② 下蹲安全：自动满足（鸟底部 > 站立顶 > 下蹲顶）
- ③ 跳跃封住：`colliderTop > 145` → `center + 31.5 > 145` → `center > 113.5`

→ `center > 121.5`，取 **center=140, yOff=105**

```
60×70 yOff=105: 碰撞体 48×63, 底=108.5, 顶=171.5

站立: 底(108.5) < 顶(90)? 108.5 > 90 ✗ 飞过头顶安全
下蹲: 底(108.5) > 顶(45) ✗ 安全
跳跃: 顶(171.5) > 底(145) ✓ 封住  底(108.5) < 顶(235) ✓ 碰撞
```

### 碰撞矩阵总表

| 玩家状态 | 小仙人掌(40×80) | 大仙人掌(60×120) | 低飞鸟(60×30) | 高飞鸟(60×70) |
|---------|:---:|:---:|:---:|:---:|
| 站立 | 碰撞 | 碰撞 | 碰撞 | **安全（飞过头顶）** |
| 下蹲 | 碰撞 | 碰撞 | **安全** | **安全** |
| 跳跃 | 越过 | 越过 | **越过** | **碰撞（空中封住）** |

> **设计意图**：低飞鸟迫使玩家跳跃（站立碰、跳跃越过），高飞鸟迫使玩家下蹲（站立安全、跳跃封住）。两种鸟形成互补策略。

## 5.11 踩坑记录（续）

### 8. `@property` 序列化值覆盖代码默认值

**现象**：修改 `PlayerController.groundY` 代码默认值后，运行时仍使用旧值，底部始终不对齐。

**原因**：`@property` 的值会被序列化到 Game.scene JSON 中。场景加载时，序列化值优先级高于 TS 代码默认值。仅改 `.ts` 文件无效。

**解决**：同步修改 Game.scene 中对应字段，或在 `onLoad()` 中用代码逻辑覆盖（如 `groundY === 0` 时自动计算）。

### 9. 拾取物与障碍物竞态重叠

**现象**：拾取物生成时位置安全，但随后障碍物生成到同一位置，导致视觉重叠。

**原因**：PickupSpawner 和 ObstacleSpawner 使用独立计时器，没有互斥机制。

**解决**：三层防护——①拾取物生成时检查障碍物 ②障碍物生成时检查拾取物（`_overlapsAnyPickup`）③运行时每 0.15 秒全量扫描清除重叠（`_cullOverlappingPickups`）。

### 10. 护盾后 1 帧内连续死亡

**现象**：护盾抵挡一次碰撞后，同一障碍物下一帧再次触发碰撞导致立即死亡。

**原因**：护盾破裂后，障碍物与玩家仍然重叠，下一帧 `_checkCollision` 再次返回 true。

**解决**：护盾触发时设 1 秒无敌帧（`_invincible`），`die()` 检测到无敌帧直接返回，给障碍物足够时间移出碰撞区。

### 11. 飞鸟 Y 坐标过高导致永远碰不到玩家

**现象**：低飞鸟 yOff=180（Y=-205）、高飞鸟 yOff=280（Y=-105），玩家站立顶仅-310，鸟始终从头顶飞过，完全起不到障碍物作用。

**原因**：yOff 原始值未经数学验证，凭感觉设定。Y 坐标系中-310 < -205，玩家在鸟下方。

**解决**：以玩家各状态碰撞体（站立顶=90、下蹲顶=45、跳跃底=145）为约束，反推 yOff：
- 低飞鸟(60×30)：yOff=65，满足站立碰撞 + 下蹲安全 + 跳跃越过
- 高飞鸟：30px 高度数学上不可能满足三条件，改为 60×70, yOff=105（飞过站立头顶 + 封跳跃）

> 注：坐标值已更新为 GROUND_Y=0 后的当前值。

### 12. GROUND_Y 从 -400 移到 0（视角垂直居中）

**现象**：所有游戏元素（玩家、地面、障碍物）集中在屏幕下半部（Y∈[-400, -165]），上半部空旷浪费。

**原因**：`GROUND_Y` 设计为 -400（Canvas 底部往上 140px），是 Chrome Dino 风格将地面放在底部的惯例。但本游戏垂直空间需求小（玩家站高 90px + 跳跃 145px + 高飞鸟 70px ≈ 305px），放在底部导致上方 2/3 屏幕空置。

**解决**：将 `GROUND_Y` 从 -400 改为 **0**（Canvas 垂直中央），同步更新：
- `GameConfig.GROUND_Y = 0`
- 场景 Ground 节点 `_lpos.y: -400 → 0`
- 场景 Player 节点 `_lpos.y: -355 → 45`（= 0 + 90/2）
- 飞鸟 yOff 参数不变（相对坐标，自动适配）
- 碰撞矩阵完全保持（AABB 使用世界坐标，差值不变）
- `GroundScroller` / `BackgroundScroller` / `UIManager` 无需修改

**新 Y 轴布局**：
```
  +540 ─── 顶部边缘
  +235 ─── 玩家跳跃峰值（顶）
  +190 ─── 玩家跳跃峰值（中心）
  +145 ─── 玩家跳跃峰值（底）
  +140 ─── 高飞鸟中心（封跳跃）
  + 80 ─── 低飞鸟中心
  + 45 ─── 玩家站立中心
    0 ─── ★ 地面（视角中央）
  -540 ─── 底部边缘
```

### 13. 高飞鸟重新设计——站立安全 + 封跳跃

**现象**：高飞鸟 yOff=85 时，站立玩家也会碰撞（collider底部=108.5 < 玩家顶部=90），与低飞鸟行为高度重叠（都是"站立碰"），两种鸟没有形成差异化策略。

**原因**：原设计目标为「站立碰到 + 跳跃封住」，但这样两种鸟对站立玩家都产生碰撞，玩家无法区分应对策略。

**解决**：将高飞鸟 yOff 从 85 改为 **105**，使其飞过站立玩家头顶，只封跳跃路线：
- yOff=105 → center=140 → collider底部=108.5 > 玩家站立顶部(90) → **安全，飞过头顶**
- yOff=105 → center=140 → collider顶部=171.5 > 玩家跳跃底部(145) → **碰撞，封锁跳跃**

**碰撞矩阵对比**：
| | 低飞鸟(yOff=65) | 高飞鸟(yOff=105) |
|---|---|---|
| 站立 | 碰撞 → 必须跳跃 | **安全** → 无需操作 |
| 下蹲 | 安全 | 安全 |
| 跳跃 | 越过 | **碰撞** → 必须下蹲 |

**设计意图**：低飞鸟 = 跳的考验，高飞鸟 = 蹲的考验，形成完整的行为互补。

## 5.12 移动端虚拟操控系统（MobileController）

> **设计目标**：为手机玩家提供可视化的虚拟按钮（跳跃/下蹲），替代键盘输入。与 PlayerController 通过 EventBus 解耦通信。

### 架构

```
触摸按下/松开
  │
  ├─ JumpButton (Button 组件 ClickEvents → 编辑器配置)
  │   └─ onClickJump() → EventBus.emit(PLAYER_INPUT_JUMP)
  │
  └─ CrouchButton (node.on TOUCH_START/END/CANCEL → 代码绑定)
      ├─ _onCrouchDown() → EventBus.emit(PLAYER_INPUT_CROUCH)
      └─ _onCrouchUp()   → EventBus.emit(PLAYER_INPUT_STAND)
          │
          ↓
PlayerController._onMobileJump / _onMobileCrouch / _onMobileStand
  → 检查 GameState.PLAYING
  → 设置 _jumpPressed / _crouchPressed 标志位
  → update → _processInput → jump() / crouch() / standUp()
```

### 设计决策

**跳跃按钮用 Button ClickEvents（编辑器配置）**：Cocos 原生的 Button 组件 ClickEvents 是最可靠的点击触发方式，不需要写触摸检测代码。在编辑器的 JumpButton → Button → ClickEvents 中配置：Target=MobileController 节点, Component=MobileController, Handler=onClickJump。

**下蹲按钮用 node.on（代码绑定）**：因为需要"按住蹲、松手站"，Button ClickEvents 只支持完整 Click 时机，不支持按下/松开分别触发。因此在 `onLoad` 中通过 `node.on(Node.EventType.TOUCH_START/TOUCH_END/TOUCH_CANCEL)` 绑定。

**Button 组件保留用于视觉反馈**：两个按钮节点上均保留 Button 组件（Transition=COLOR），按下时 Sprite 颜色自动加深，松手恢复。交互逻辑由代码/ClickEvents 处理，视觉过渡由 Button Transition 自动完成，两者互不干扰。

**PlayerController 改造**：移除内嵌的 `input.on(TOUCH_START/TOUCH_END)` 触摸处理，改为监听 EventBus 的 PLAYER_INPUT_* 事件。键盘输入（Space/↑/↓）保留用于 PC 开发调试。

### 事件流（全链路）

```
按 JumpButton
  → Button ClickEvent → MobileController.onClickJump()
  → EventBus.emit(PLAYER_INPUT_JUMP)
  → PlayerController._onMobileJump → GameState 检查 → _jumpPressed=true
  → update → _processInput → jump() → _velocityY=900 → state=JUMPING ✅

按下 CrouchButton
  → node.on(TOUCH_START) → MobileController._onCrouchDown()
  → EventBus.emit(PLAYER_INPUT_CROUCH)
  → PlayerController._onMobileCrouch → _crouchPressed=true
  → update → _processInput → crouch() → scaleY=0.5 → state=CROUCHING ✅

松开 CrouchButton
  → node.on(TOUCH_END/CANCEL) → MobileController._onCrouchUp()
  → EventBus.emit(PLAYER_INPUT_STAND)
  → PlayerController._onMobileStand → _crouchPressed=false
  → update → _processInput → standUp() → scaleY=1 → state=RUNNING ✅
```

## 5.13 金币计数 & 分数显示系统（ScoreDisplay + CoinCounter）

> **设计目标**：将分数显示逻辑从 UIManager 中分离为独立组件，提高内聚性；新增金币计数器，统计本局拾取金币数量并持久化历史累积总数。

### 架构概览

```
PICKUP_COLLECTED(type, points)
      │
      ├──────→ CoinCounter._onPickupCollected
      │           │  type === PickupType.COIN
      │           ├─ _currentCoins++
      │           └─ coinLabel.string = "× N"
      │
      └──────→ GameManager._onPickupCollected
                  └─ addScore(points) → emit(SCORE_CHANGE, totalScore)

SCORE_CHANGE(score)
      │
      └──────→ ScoreDisplay._onScoreChange
                  └─ currentScoreLabel.string = padStart(score, 5)
```

### 设计决策

**ScoreDisplay 从 UIManager 分离**：UIManager 原有 `updateScore()` / `updateHighScore()` / `_onScoreChange()` 等分数相关方法和属性，职责混杂（面板切换 + 分数渲染）。分离后 UIManager 只负责面板显隐切换，通过 `@property(ScoreDisplay)` 持有引用，在合适的时机调用 ScoreDisplay 的公有方法。

**CoinCounter 监听 PICKUP_COLLECTED 而非 SCORE_CHANGE**：SCORE_CHANGE 每帧都触发（距离分累积），如果 CoinCounter 监听它会频繁无效更新。直接监听 PICKUP_COLLECTED 并过滤 `type === PickupType.COIN`，只在真正捡到金币时才更新，性能最优。

**金币累积持久化**：每局结束时 `_totalCoins += _currentCoins`，写入 `sys.localStorage`（key=STORAGE_TOTAL_COINS）。不保存每局中间值，只保存累积总和。

## 5.14 星级评定系统（StarRating）

> **设计目标**：游戏结束后根据最终分数评定 1-3 星，在结算界面逐颗弹出展示，给玩家明确的表现反馈。

### 星级阈值

| 星级 | 分数区间 | 对应游戏阶段 |
|------|----------|--------------|
| ★☆☆ | 0 ~ 1000 | 新手~中速阶段（速度 ≤600） |
| ★★☆ | 1000 ~ 2500 | 快速阶段（速度 750~900） |
| ★★★ | 2500+ | 高速阶段，需在 900+ px/s 存活 |

> **阈值决策**：初版方案为 2 星 200 / 3 星 800，实测过于宽松（熟练玩家常规可达 2000+ 分）。上调为 1000/2500，与难度曲线的分数档位对齐，3 星需在最高难度区间坚持一段时间才有含金量。阈值为 `@property` 可在编辑器调整。

### 架构

```
GameManager.gameOver()
  → emit(GAME_OVER, finalScore, highScore, isNewRecord)
    → UIManager._onGameOver()
      → scoreDisplay.updateFinalScore / updateHighScore / showNewRecord
      → starRating.evaluate(score)
        → reset()                    # 取消未完成动画 + 隐藏全部星星
        → count = getStarCount(score)
        → scheduleOnce(0s)   → Star1.active = true
        → scheduleOnce(0.4s) → Star2.active = true (count≥2)
        → scheduleOnce(0.8s) → Star3.active = true (count≥3)
```

### StarRating 组件

**文件**：`assets/scripts/ui/StarRating.ts`
**挂载**：GameOverPanel/StarContainer 节点

```typescript
@ccclass('StarRating')
export class StarRating extends Component {
    @property([Node]) starNodes: Node[];     // 3 个星星节点，从左到右拖入
    @property threshold2Stars: number = 1000; // 2 星最低分
    @property threshold3Stars: number = 2500; // 3 星最低分
    @property animateInterval: number = 0.4;  // 每颗星弹出间隔（秒）

    evaluate(score: number, onComplete?: () => void): void; // 评定并逐颗展示
    getStarCount(score: number): number;                    // 纯计算 1-3
    reset(): void;                                          // 取消动画 + 全部隐藏
}
```

### 设计决策

**UIManager 直接调用而非监听 GAME_OVER**：StarRating 仅在结算面板展示时工作，由 UIManager 通过 `@property(StarRating)` 引用并在 `_onGameOver` 中调用 `evaluate(score)`，与 ScoreDisplay 的调用方式保持一致，避免多个组件重复监听同一事件。

**`unscheduleAllCallbacks` 防残留**：`reset()` 先取消所有未完成的 scheduleOnce，防止玩家在星星弹出动画期间快速重开导致上一局的回调在下一局结算时补触发。

**占位方案**：星星用 Label 显示 Unicode `★`（U+2605，字号 64，金色 #FFC800），初始不激活。后续有贴图时将 Label 替换为 Sprite 即可，组件代码无需修改（只操作 `node.active`）。

### 编辑器配置步骤

1. **GameOverPanel 下新建 StarContainer 节点**：UITransform(300×80)，添加 `StarRating` 组件
2. **创建 3 个星星子节点**（初始均不激活）：
   - Star1 (-100, 0) / Star2 (0, 0) / Star3 (100, 0)
   - 各挂 Label：文字 `★`，字号 64，颜色 #FFC800
3. **绑定 StarRating 属性**：Star Nodes 按顺序拖入 Star1/Star2/Star3；阈值 1000 / 2500；间隔 0.4
4. **绑定 UIManager 属性**：ScorePanel 的 UIManager 组件 → Star Rating 拖入 StarContainer 上的 StarRating 组件

|------|------|

| `assets/scripts/ui/UIManager.ts` | **修改**，新增 `@property(StarRating)` + `_onGameOver` 中调用 `evaluate(score)` |

## 5.15 地面瓦片显示 Bug 修复

> **Bug**：游戏刚开始屏幕右侧出现大面积地面空白（"有一段路没有显示出来"）。
>
> **根因**：两个瓦片启动时位置重叠在 (0,0) + 回收阈值调整引入时序问题。

### Bug 发现过程

| 阶段 | 修改 | 问题 |
|------|------|------|
| **原始代码** | 两瓦片默认位置 (0,0)，完全重叠 | `start()` 无定位逻辑，`_onGameRestart` 才排列。首次启动瓦片重叠，滚动后右边空白 |
| **第一版修复** | `start()` 中调用 `_resetTilePositions()` 排列瓦片 | 初始定位修复，但 2 瓦片阈值还是 -1920（右边缘刚好在摄像机左边缘，零缓冲） |
| **第二版修复** | 阈值改为 `-2880`（`-_tileWidth * 1.5`） | 引入新 Bug：2 瓦片系统下，Tile0 多等 2.4s 才回收，Tile1 已移过 x=0，右半边屏幕空白 |
| **第三版修复** | 添加 `_ensureTileCount(3)` 动态克隆第 3 瓦片 | 代码中用了 `Node.instantiate()` —— Cocos Creator 3.x 中不存在此 API，抛出异常导致 `start()` 中断 |
| **最终修复** | `Node.instantiate` → `instantiate`（独立函数导入） | 三瓦片 + `-2880` 阈值，数学验证无缝隙 |

### 根因分析

**根因 1 — 初始定位缺失**：场景中 GroundTile_1 和 GroundTile_2 的 `_lpos` 均为 `(0, 0, 0)`，两瓦片完全重叠。`_onGameRestart()` 中有正确排列逻辑但不在首次启动时调用。

**根因 2 — 两瓦片系统的数学限制**：
```
屏幕宽 1920, 瓦片宽 1920, 2 块瓦片初始位置 [-960, 960]

当 Tile0 到达 -2880 (阈值) 时:
  Tile1 = -960 (已偏移 1920px)
  Tile1 覆盖 [-1920, 0] → 屏幕只看到 [-960, 0]
  屏幕右半 [0, 960] 全空 ❌

2 瓦片下安全阈值上限 = -1920 (恰好无缝隙)
任何小于 -1920 的阈值必然产生右半屏幕缝隙
```

**根因 3 — API 误用**：`instantiate` 是 `cc` 模块导出的独立函数（与 `ObjectPool.ts` 中用法一致），而非 `Node` 的静态方法。`Node.instantiate(original)` 在运行时抛出 `TypeError`。

### 最终方案

1. **三瓦片系统**：`start()` 中调用 `_ensureTileCount(3)` 动态克隆补齐 3 块瓦片
2. **回收阈值**：`-_tileWidth * 1.5 = -2880`，瓦片右边缘超过摄像机左边缘 960px 后才回收
3. **容器安全**：`update()` 中 `length < 3` 时提前返回
4. **正确 API**：`import { instantiate } from 'cc'`，使用 `instantiate(original)` 克隆

### 三瓦片验证

```
初始: T0@-960  T1@960  T2@2880  → 屏幕全覆盖 ✓
回收: T0@-2880 T1@-960 T2@960   → T1左半+T2右半覆盖屏幕 ✓
      同一帧 T0 移至 T2 右侧 @2880 → 无可见闪烁
```

| 参数 | 值 |
|------|-----|
| 瓦片数 | 3（自动补齐） |
| 回收阈值 | -2880（`-_tileWidth × 1.5`） |
| 缓冲距离 | 960 px（半瓦片宽度） |
| 回收周期 | 4.8 秒（1920 px / 400 px·s⁻¹） |
| 缝隙验证 | 任意时刻屏幕全覆盖 ✓ |

| `assets/scenes/Game.scene` | 无需改动（瓦片在运行时动态克隆） |
